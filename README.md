# wheel_speed_monitor

RC 攀爬车四轮转速监测验证台（v1）。

A3144 霍尔传感器 + 小铷磁铁随车轮转动触发脉冲，ESP32-S3 用 PCNT 硬件计数，
经 WebSocket 推送遥测帧到内嵌网页验证台。采集器框架可扩展（后续加 IMU 姿态等）。

## 硬件与接线

板卡：Freenove ESP32-S3 WROOM CAM（FNK0085）。摄像头已接线但 v1 不启用。

| 轮 | 霍尔 GPIO | 说明 |
|---|---|---|
| 左前 | GPIO1 | |
| 右前 | GPIO14 | 闪光灯焊盘可选接口，不用 |
| 左后 | GPIO21 | |
| 右后 | GPIO47 | |

A3144 接线：VCC ← ESP32 3.3V（**注意：数据手册标称 4.5–24V，3.3V 低于规格下限，
可能工作但不保证**）、GND ← GND、OUT → GPIO 并 10kΩ 上拉到 3.3V（面板已加）。
磁铁南极靠近 → OUT 拉低（下降沿 = 一次触发）。

### 3.3V 供电排查预案

1. 打开验证台「原始 IO 电平监视」：
   - 静止时 4 路全"高" = 上拉有效；某路非高 → 查该路接线/上拉电阻。
   - 磁铁靠近时对应 GPIO 闪"低" = 触发正常。
2. 静止高、磁铁靠近不闪低 → 万用表量 A3144 VCC 对 GND 电压：
   - 不足 3.1V 且无动作 → **改 5V 供电**：VCC 改接 ESP32 5V 引脚；
     **输出上拉保持接 3.3V**（A3144 是开集电极，上拉电压决定 GPIO 高电平，安全）。
3. 翻转但 RPM 乱跳 → 磁铁南极面朝向传感器、间距 < 5mm；网页「去抖」填 20 开软件去抖。

## 差速舵机

前、后差速各接一个标准角度舵机（50Hz，脉宽 500–2500µs，1500µs 中位）。
信号线接 **GPIO41（前差速）** 和 **GPIO42（后差速）**。

自动模式下每个通道只有两个落点，各自可配：**解锁档**是正常行驶位置，
**锁定档**是差速锁死位置。差速器只有锁止和释放两个确定位置，中间行程没有意义，
所以不做连续的角度映射。前后轴分别配置——两轴舵机的安装朝向或连杆行程不同时，
各填各的行程端即可（比如后轴装反，就把它的锁定档填到另一端），不需要「反向」开关。

这两个脚在 ESP32-S3 上是 JTAG 引脚，但默认的调试通道是芯片内置的
USB-Serial-JTAG，它走芯片内部的 TAP 控制器，不占用这四个引脚，所以照用不误：
不用关 JTAG，不用改 console，烧录和 monitor 的用法一个字都不变。唯一会撞的
情况是有人烧了 `DIS_USB_JTAG` efuse 把 JTAG 引到引脚上。

舵机电源必须独立 5V 并与 ESP32 共地。堵转电流可能超过 1A，不要从板子的
3.3V 取电。

### 在验证台上验证（不接真舵机）

设置 tab 里勾上「模拟舵机模型」，执行器就换成软件模型：它按设定速率朝目标
脉宽移动，把"指令到哪、现在到哪、到没到"如实回传页面。轮速照旧用模拟模式喂，
整条判定链跟接了真舵机时走的是同一份代码。

能在验证台上复现的几件事：

| 想看的现象 | 怎么设 |
|---|---|
| 锁定差速 | 模拟转速设成左前 200、其余 60。前轴速差比例 0.7，超过 0.30 的门槛，前差速跳到锁定档 |
| 锁上后不被轮速带跑 | 锁定期间把左前改回 60，前差速继续锁着，不会马上松 |
| 试探与退避 | 保持时长（默认 3 秒）走完，状态变「试探中」、脉宽回解锁档。这时再制造打滑会立刻锁回，保持时长翻倍到 6 秒，再往后 12 秒，封顶 30 秒 |
| 退避复位 | 四个轮子都设成 60，或者全部停到 0。试探窗口走完就回到「已解锁」，保持时长复位成 3 秒 |

页面上的阶段徽章（已解锁 / 锁定中 / 试探中）和三段式状态机是一一对应的，
锁定保持时长的翻倍也在卡片上直接显示。

### 接真舵机

设置 tab 里取消勾选「模拟舵机模型」，执行器切成 LEDC 输出。轮速仍然可以用
模拟模式喂，这正是"用验证台的模拟轮速驱动真舵机"的用法。

拿示波器或逻辑分析仪量 GPIO41/42：应当是 50Hz 方波，脉宽等于页面显示的指令
值。通道关掉时引脚停在低电平、没有脉冲，舵机脱力。真实舵机的行程时间比模拟
模型慢，如果试探窗口（默认 2000ms）不够它走完，在设置页调大即可。

## 构建与烧录

```bash
# 环境加载（每次新终端）
get_idf

# 首次
idf.py set-target esp32s3
idf.py build

# 烧录（端口先 ls /dev/cu.*）
idf.py -p /dev/cu.usbmodemXXX flash monitor
```

## 使用

1. 烧录后手机/电脑连 WiFi 热点 `wheel-bench`（开放，无密码）。
2. 浏览器打开 `http://192.168.4.1`。
3. 页面分两个 tab：
   - **监测**：4 轮 RPM/线速度/频率/累计脉冲、轮速曲线、原始 IO 电平监视、
     差速舵机状态卡。
   - **设置**：采集配置（磁铁数/轮径/EMA/去抖/每轮启用）、模拟模式转速、
     差速舵机的全部参数。
4. 配置自动持久化到 NVS。「模拟模式」用合成数据跑完显示与计算链路，
   走的是和真实霍尔完全相同的那条数据链。

## 宿主机单元测试

```bash
cmake -S tests/native -B tests/native/build
cmake --build tests/native/build
ctest --test-dir tests/native/build --output-on-failure
```

纯逻辑层（数学、回绕判定、模拟源、采集框架、JSON 渲染、配置校验、差速状态机、
模拟舵机模型）在 macOS 用 clang + Unity 跑；硬件层（PCNT、LEDC、NVS、WiFi）
与页面是集成分层，由板上验证台验证。

## 目录结构

```
main/           入口、配置、Web 服务、内嵌验证台页
components/
  telemetry/    采集框架（注册表/采样泵/帧聚合），可扩展采集器
  wheel_speed/  轮速采集器实现（数学链/回绕/模拟源/JSON 渲染）
  wheel_sensor/ PCNT 硬件薄封装（A3144 4 路）
  strategy/     差速状态机（打滑判定/锁定保持/试探退避/脉宽映射）+ JSON 渲染
  servo_act/    舵机执行器接口 + 模拟模型（纯 C）
  servo_drv/    LEDC 硬件输出（IDF 依赖）
tests/native/   宿主机单测（clang + Unity + ctest）
```

## 扩展：新增采集器（如 IMU）

1. `telemetry.h` 的 `telem_type_t` 末尾加枚举值；
2. 实现 `telem_collector_ops_t`（init/sample/render/reset_baseline）；
3. `app_main` 里 `telem_register` 注册；
4. 前端 `applyFrame` 的 collectors 遍历加一个渲染函数。

协议约定：`sample` 每采样窗口调用一次（50ms），计算量须小；`render` 输出本类型
JSON 对象（不含外层包裹），字段名即前端协议，变更需前后端同步。
